# Agent 启动、执行与交接手册

状态：本仓库已被用户指定为实施目标。计划已迁入仓库作为唯一活跃来源。恢复本次工作时复用已记录的 worktree，不再新建实现目录。

## 1. 给首个 Agent 的启动提示

下面的提示可以直接交给编码 Agent。用户必须先提供真实仓库路径，不能保留未填写值后自行猜测。

```text
目标：实施 Computer Use 插件的下一张已满足依赖的任务卡。
产品定位：模型无关、macOS 原生、语义目标优先、执行前重验、默认后台协作、结果有证据、用户可接管。

先确认用户指定的目标仓库绝对路径。没有路径，就停在 CU-000 并报告缺失项。
不要在计划资料包、第三方参考 checkout 或 DSH 安装目录中写插件实现。

进入仓库后：
1. 读取 AGENTS.md、ARCHITECTURE.md、产品定义、接口约定、安全说明和总执行计划。
2. 检查 Git base、未提交改动、实际 package manifest 和宿主版本。
3. 从 Progress log 确认上一张任务卡的真实证据，不把复选框当证明。
4. 只选择一张依赖已完成且授权已满足的任务卡。
5. 写出本次范围、允许修改文件、要保护的不变量和准确验证命令。
6. 先写失败测试，再实现最小行为，再运行针对性测试和回归。
7. native 能力只能在用户批准的 fixture/测试副本中验证。
8. 未知是否生效的动作不得重试。后台失败不得静默改前台或全局输入。
9. 完成后更新任务、Progress log、质量与缺口记录，提交交接摘要。

禁止自动安装到用户 Profile、修改 DSH Core、操作真实高影响业务、推送或发布。
没有凭据、TCC 或审批能力时记录 not_run/blocked，不伪称通过，不绕过。
```

## 2. 每张任务卡的开工检查

- 目标仓库由用户明确指定。
- 读取仓库自己的指令，不能拿本资料包覆盖已有规则。
- 如果目标仓库已有文档，将本计划作为提案迁入并链接，不盲目覆盖 AGENTS.md。
- 记录当前 commit、工作树差异和属于用户的文件。
- 依赖卡交付物真实存在且相应测试证据可复核。
- 只使用真实 manifest 中存在的命令。
- 在实施前按可用宿主工具创建隔离工作树；只读检查不需要。遵守仓库既有工作流。
- 计划中的 source 路径若与实际仓库不同，先更新一次映射，不在代码里维护两套模块。
- 如果同一变更需要多个 reviewer 或 native 机器，先记录协调方式，不假定资源存在。

## 3. 最小任务执行流程

1. 写出一条可失败的验收断言。
2. 运行并确认失败原因是缺少目标行为，而不是环境错误。
3. 实现最小切片，不附带无关重构。
4. 运行该断言至通过。
5. 运行任务卡要求的回归命令。
6. 检查授权、错误、取消与隐私负向路径。
7. 审查 diff 与生成产物一致性。
8. 记录执行命令、退出码、测试编号和证据位置。
9. 缺必需 native lane 时保留任务 pending 或 blocked，不勾完成。
10. 提供交接，不自动进入未授权的发布或真实 UI 操作。

TDD 不要求先让整个包构建失败。schema、协议和文档也可以用最小合同断言验证。mock 通过不替代 native 验收。

## 4. 持续记录

建议在真实仓库创建执行证据记录。具体格式由 CU-002 冻结，不把敏感原始数据入库。

最低字段：taskId、runId、baseCommit、resultCommit/diff、hostVersion、protocolVersion、helperDigest、command、exitCode、testIds、result、skipReason、artifactRefs、nextTask。

基础重跑用 [固定验证器](<../design-docs/foundation-verification.md>)：`node scripts/verify-foundation.mjs`，只有明确要跑fixture只读AX才加`--native-observation`。JSON stdout记录实际8步/分母、包括untracked的限定源码前后指纹/HEAD/dirty；默认exit0不是MVP完成，显式缺TCCexit3仍NOT_RUN，NO_GO恒定。可以单独留存本机报告但不得把报告混入宿主Session审计；docs/model/UI/real-app/生产输入不在8step通过范围。

- deterministic 证据与模型 trace 分开。
- 长日志可保留脱敏的文件和摘要，不把整个终端输出贴进计划。
- ScreenshotRef 必须按保留期管理。测试证据不豁免隐私规则。
- 实际 command 与计划不同时，说明变更理由并更新命令表。

## 5. 标准交接格式

```text
任务：CU-xxx
状态：completed | in_progress | blocked
范围：本次只完成什么
仓库：用户确认的目标路径
基线：commit；是否有预存修改
变更：实际文件和关键行为
合同：是否改 schema/native protocol/policy 默认值
证据：命令、退出码、验收编号、记录路径
红/绿：初始失败原因与修复后结果
未运行：测试层、原因、是否阻断本卡完成
安全：权限、目标、取消、重放、隐私是否有新边界
已知问题：具体风险，不用“可能还有问题”代替
下一步：一张依赖已满足的任务卡
需要人类决定：明确选项与影响；没有就写无
```

路径指向实际存在的文件。不能用不存在的 PR、commit 或测试结果占位。

## 6. 停止条件

遇到以下任一条件，不继续 native 输入，不通过其它工具换路线：

- 操作对象无法唯一绑定，或授权目标与当前窗口不一致。
- 模型参数试图覆盖可信身份、权限或宿主模式。
- 审批不可用、拒绝、撤销、过期或上下文改变。
- 用户接管，或控制 broker/锁不可用。
- native timeout/断连后无法判断动作是否已生效。
- 背景操作必须抢前台/全局鼠标才能完成。
- 测试会接触真实私人账号、付款、对外发送、不可逆删除或系统授权。
- 发现机密日志、跨 workspace artifact、未知副作用或 helper 产物不一致。

停止后给出 phase、已知执行状态、安全下一步。不要把停止等同回滚。

## 7. 并行与审查

- 仅协调 Agent 能改任务依赖与公共合同。
- 子 Agent 获得完整任务卡、固定接口、允许写集和非目标。
- 共享 service/native dispatcher/package manifest 任务串行。
- reviewer 使用独立上下文，先复核证据，再评价完成状态。
- 子 Agent 返回“已完成”不等于协调者已验证。
- 若 reviewer 发现阻断问题，追加修复卡并重跑相关测试，不隐藏原结果。

## 8. 从中断恢复

重新读取仓库状态、计划、最新证据和 diff。不要只依赖聊天总结。查明 helper/broker 是否仍活着、是否有 unknown action、受管输入是否释放。

控制授权、批准 token 和观察句柄不跨重启恢复。恢复只能读取去敏 action ledger 来阻止重放，不能据此自动补执行。

恢复文档状态后选择下一张卡。仍缺审批或 TCC 的阶段继续停止，不把用户说“继续”解释为授予所有系统权限。
